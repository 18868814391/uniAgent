# dev-code-change（改码工作流）

任何「改代码 / 修 bug / 加功能 / 重构」任务的主流程。别跳步：绝大多数改坏代码的事故都出在「没读原文就改」和「改完不自检」。

## 流程

1. **定位 + 读项目约定**：先看系统提示词【项目级上下文】段里有没有这个项目的 `AGENTS.md`（应用会自动注入）；没有就 `read_file <仓库根>/AGENTS.md`。它写着这个项目用什么组件、参考哪个页面、跑什么命令——**先读它再动手，比事后返工便宜得多**。然后 `grep_code` / `glob_files` 找目标，**必须传 path**（指向具体仓库/模块目录，不传会扫全授权盘）；能猜文件名片段先 glob 再精读。找定义不只看一处——用 grep 反查**调用方**，确认改动影响面。
2. **先出改动计划 + 批量读（决定往返次数的一步，别跳过）**：把要改的文件（绝对路径）、每个文件改什么（一两句）、怎么验证写清楚；**同时把这次要精读的文件在同一条消息里并行 `read_file` 一次读完**。工具支持一轮读/改多个文件，用足它。反例就是"读一个文件 → 改一处 → 再读下一个"——那是改码慢的头号原因。计划读完后可以修正一次，但不要退化成边读边改：**若已经第 20 轮还没开始 `edit_file`，停下来**，多半是在猜路径或重复检索，去读 `AGENTS.md` 或直接问用户。常规改码的目标是 **15 轮以内**。**若属「重构 / 替换封装组件 / 迁移写法」类任务，计划里还要额外输出一张「原实现行为清单」**（模板见下方专节）—— 这类任务丢的从来不是代码，而是封装层那些"看不见的行为"。

   **计划要同时落成结构化清单**：调 `update_todos` 把步骤写进去（3~8 条，每条一句话）。清单会在每轮请求末尾被系统**原样回显**给你，同时用户也能在界面上看到 —— 不要靠记忆推进，也不要每轮重复调用（会被判成重复调用拦下）。每真正做完一项（含验证）就更新一次。**做完不要清空清单**——直接给最终回答、清单保留（用户要对着它核对结果）；只有用户明确要求清空或整个计划作废时才传空数组 `[]`。规则细节见系统提示词的【任务清单】段。
3. **改前精读**：`read_file` 完整读目标文件（至少读目标函数前后足够上下文）。确认三件事：这段代码被谁调用、依赖什么、有没有同构的兄弟实现（改一处常要同步改另一处）。**禁止不看原文凭记忆改**。
4. **精准编辑**：优先 `edit_file`（str_replace），只改要改的部分；`old_string` 必须与原文逐字符一致（含缩进），多处出现时加更多上下文做成唯一，或明确用 `replace_all`。只有新建文件 / 整文件重写才用 `write_file`。**多个文件互不依赖时，在同一条消息里并行发起多个 `edit_file`**；同一个文件的多处改动也尽量一轮发完。
   **改完不要重读全文确认**——`edit_file` / `write_file` 的返回里带 `diff` 字段（unified diff，变更行 ±3 行上下文），**扫一眼 diff 就能确认改动落对了地方**，比 `read_file` 读回整个文件省一整轮往返、也省上下文。
   - 看到 `+` 行里有你没打算写的内容 → `old_string` 匹配到了错误位置，立刻停下重新定位，别将错就错。
   - 看到 `diffTruncated: true` → diff 只展示了部分改动（尾部会说明省略了多少），**不能据此认为改动已完整**，必要时再 `read_file` 核对。
   - 改动大到 diff 几乎全是 `+`/`-` → 说明该用更小的 `edit_file` 粒度，而不是整文件重写。
5. **自检**：按 `dev-self-check` 技能执行（语法检查按**目录**跑，不是只跑改过的文件；Vue/TS 项目跑 eslint --fix + SFC 编译校验；默认**不跑**全项目类型检查和全量 build）。
6. **清理 AI 味**：对照 `git diff` 按 `dev-rmslop` 扫一遍 —— 删掉模型顺手加的翻译式注释、
   上游已校验过的重复判空、`as any`。只清本次引入的，不碰存量。
7. **沉淀**（有踩坑才做）：本次若遇到误导性报错、隐藏耦合、README 里没有的命令，
   按 `dev-learn` 写进对应层级的 `AGENTS.md` —— 下次应用会自动注入，不用重踩。
8. **汇报**：先结论 → 后表格 → 带文件路径。报三件事：**改了哪些文件、关键改动是什么、验证结论是什么**。验证失败照实说，疑似存量问题用 HEAD 版本对照证明（见 `dev-git-discipline`）。

## 重构 / 替换封装组件：等价性核对清单（最容易漏东西的一类任务）

把某个封装组件换成另一套写法（典型：`ht-table-page` → `ht-search` + `HtTable`）时，
**漏掉的从来不是被改文件里的代码，而是封装层默默提供的"隐式行为"** ——
它们不在调用方代码里，只读被改的那个文件根本发现不了。

**默认要求「对外行为完全等价」**：除非用户明确要求改行为，否则首屏加载、请求参数、事件、插槽、样式一个都不能变。
**出计划时先把这张表填出来，改完逐条打勾、再汇报**：

| 隐式行为 | 典型表现 | 实例（ht-table-page → ht-search + HtTable） |
| --- | --- | --- |
| **生命周期里自动做的事** | 封装层在 `onMounted` 里自动发起首屏查询 / 初始化 | 原组件内部自动触发首查 → 拆开后必须自己补 `onMounted` 触发 |
| **往下透传的默认 props** | 布局尺寸、分页、序号、复选框等默认值由封装层注入 | `maxHeight:'100%'`、`showOverflow:'tooltip'`、`size:'large'`、`isPager`、`isCustom`、`isDefaultSymbol`、`isChecked`、`keepCheckedRows` |
| **透传给子组件的 props** | 权限码、自定义列存储 key 等 | `permission-code`、`id`（**自定义列配置的存储 key，变了用户的自定义列就全丢**） |
| **转发的事件** | 封装层把子组件事件加工后再 emit | `@search`（封装层会先合并 defaultParams 再 emit）、`@handle-change` |
| **暴露给 ref 的方法 / 属性** | 调用方大量使用 `pageRef.value.xxx` | `search.form / options / formatParams()`、`table.vxe / tableData / reLoadTable()` |
| **合并进请求的默认参数** | 封装层调接口前统一 merge | `defaultParams: { isComplete: 0 }` —— **列表、合计、导出三条链路都要生效** |
| **插槽** | 表头排序、单元格渲染、footer 合计 | 全部原样搬到新组件，一个不落 |
| **外层样式 / 布局类名** | 全局样式按这些类名挂载 | `class="xmycfx"`、`p-list-container`、`table-section-container` |

**核对时机**：改完之后、汇报之前。汇报里要能看出「原行为 → 改后对应写法」的逐条对应关系；
任何一项确认不了（例如"进页面到底还会不会自动查数据"），**明确标出来问用户**，不要默认它没问题。

⚠️ 这类任务的典型事故（**都不报错**，功能看起来还对）：进页面不再自动查数据、自定义列配置失效（id 变了）、
合计/导出漏了默认参数、样式高度塌了、勾选状态丢了。**关掉思考模式时尤其容易漏** —— 靠直觉过一遍是补不上这些的，
只能靠这张表逐条比对。

## 边界

- **不做没被要求的优化**：不顺手重构、不改无关格式、不「顺便」升级依赖。改前端就只改前端，不主动去后端仓库 grep 找答案——除非用户明确要求。
- **改项目内的文件不用问**：目标在 git 仓库内就放手改（改完汇报改了哪些文件、怎么验证的即可）；只有系统级路径、不在仓库内的文件、未被 git 跟踪/带未提交改动的删除、批量操作与危险命令才先 `ask_user`——判定口径见 `conventions/dev/dev-conventions.md` 第 2 节，应用侧 `tools/guard.js` 按同一套规则弹确认框。
- 方案有多个合理选项、或要动的文件超出用户指明范围 → 先 `ask_user` 对齐再动手。
- 改完代码不主动 commit / push（见 `dev-git-discipline`）。
