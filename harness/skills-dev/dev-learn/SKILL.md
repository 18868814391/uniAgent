# dev-learn（把学到的东西写进 AGENTS.md）

改造自 opencode 的 `/learn` 命令。用途：一次调试踩坑、一个隐藏耦合、一条没写进 README 的命令，
**当场**写进对应层级的 `AGENTS.md`，下次再碰这个目录时应用会自动把它注入上下文 —— 不用重新踩。

这是「项目级约定」机制的上游。应用的 `electron/agents-md.js` 负责**读**（从仓库根一路读到目标目录，
注入系统提示词【项目级上下文】段）；本技能负责**写**。只读不写，约定就会腐烂成过期文档。

## 往哪一层写（分层是关键）

`AGENTS.md` 可以放在**任意目录层级**，不只在仓库根。越靠近相关代码，命中越准：

| 发现的性质 | 写到哪 |
| --- | --- |
| 跨模块的、项目级的（构建命令、包管理器、技术栈禁忌） | `<仓库根>/AGENTS.md` |
| 某模块/包专属（如 `electron/` 的进程模型、`src/` 的状态管理） | `<模块>/AGENTS.md` |
| 某功能目录专属（如 `src/views/transportBill/`） | `<功能目录>/AGENTS.md` |

目标文件不存在就新建。**不要为了省事全塞进仓库根** —— 那会变成新的「巨型 README」，
反而挤占每次注入的上下文预算。

## 什么算「值得写」（只收非显而易见的）

- 文件/模块之间**隐藏的耦合**：改 A 必须同步改 B，否则静默出错
- 执行路径与代码「看起来的样子」不一致的地方
- 非显而易见的配置、环境变量、命令行开关
- **误导性报错**：错误信息指向 X，真因在 Y（这类最值钱，下次能省一整轮排查）
- 工具/API 的怪癖与绕过办法
- README 里没有的构建 / 测试命令
- 架构决策与其约束（为什么这么做、不能怎么改）
- 必须一起改的文件组

## 什么不要写

- 文档里已有的、看 README 就知道的事实
- 语言/框架的标准行为（「Vue 的 ref 要 .value」这种别写）
- 已经在某个 `AGENTS.md` 里的（先读再写，不要重复）
- 长篇解释 —— 一条 1~3 行，说清「是什么 + 为什么 + 怎么办」
- 只对本次会话成立的临时信息

## 流程

1. **回看会话**：哪些地方试了两次以上才通？哪个报错把人带偏了？哪两处改动被迫同步？
2. **定层级**：这条发现管的是多大范围？
3. **先读后写**：`read_file` 目标层级的 `AGENTS.md`（含仓库根），确认不是已有内容；
   全都没有就先看仓库根有没有，没有则新建。
4. **写入**：用 `edit_file` 追加到合适的小节下；新建文件用 `write_file`。保持该文件既有风格
   （有的用 `## 标题` 分节，有的就是平铺条目 —— 跟着它走）。
5. **控长度**：每条 1~3 行。`AGENTS.md` 是给模型读的，不是给人写报告的地方 ——
   应用对注入总量有上限（`agents-md.js` 里 `MAX_TOTAL_CHARS`），写太胖会挤掉后面的文件。

## 收尾汇报

报三件事：**新建/更新了哪些 AGENTS.md**、**各写了几条**、**每条一句话是什么**。
不要贴全文。

## 与其它技能的关系

- 改码主流程见 `dev-code-change`；本技能是它的**收尾动作** —— 一次改码任务里踩到的坑，
  在汇报前顺手沉淀。
- 写入的是项目内文件（在 git 仓库里），按 `dev-conventions.md` 第 2 节属于**免问**档，
  直接写、汇报里说明即可。
