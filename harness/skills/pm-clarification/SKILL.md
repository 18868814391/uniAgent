# pm-clarification（需求澄清）

## 硬性闸门（先过这一关，不满足就退出）

先判型：本条消息若属于**询问既有系统逻辑**——用户在问系统现在怎么运作、为什么这样、有哪些状态、是否允许创建/操作、某字段或按钮的口径，而没有「设计 / 新增 / 产出 PRD 原型」的委托诉求——**不要进入本技能**。直接按通用方式用 `grep_code` / `read_file` / `read_file` 检索 ERP 代码回答；禁止 `ask_user`、禁止写澄清卡。若拿不准方向，先给判断并最多用一次 `ask_user` 确认「查现有逻辑 vs 落成新需求」，再决定是否继续本流程。

## 适用

- 用户只有一句想法、目标/入口/范围/端别不清。
- 新增/优化/修复类型不明。
- 需要在动手设计前把需求收敛。

## 步骤

1. **识别缺口**：对照以下清单逐项判断哪些已知、哪些未知：
   - 目标对象（做什么事、给谁用）
   - 功能入口（挂在哪：菜单/路由/业务对象）
   - 端别（PC / H5 / 移动）
   - 范围与非目标（这次做不做）
   - 关键字段与口径
2. **先查代码**：能通过 `glob_files / grep_code` 定位业务对象/菜单、`grep_code` 定位现有页面/接口的，先查再问，减少无谓提问。
3. **ask_user 澄清**：只问阻塞下一步的 1 个核心问题（遵守 `ask-user-rules.md`）。
4. **收口成卡**：把结论整理成澄清卡，写入 `{{PRODUCT_OUTPUT_DIR}}/work/<任务slug>/pm-clarification-card.md`。

## 澄清卡模板

```markdown
# 需求澄清卡：<功能名>

- 目标对象：xxx
- 功能入口：xxx
- 端别：PC
- 范围：xxx / 非目标：xxx
- 关键字段：xxx

## 已确认
- xxx

## 推断
- xxx

## 待确认
- xxx（向用户提问过 / 待用户确认）
```
