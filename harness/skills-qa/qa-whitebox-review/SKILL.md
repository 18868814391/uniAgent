# qa-whitebox-review（白盒源码审查）

## 适用

- 白盒测试主流程的逐条核对环节。
- 基于测试用例 + 代码路径，做源码级静态功能验证（不运行代码、不启动服务）。

## 执行流程

### Step 1 建立代码证据链

按真实调用链追代码，不只盯入口（**仓库与分支随运行平台变化**，下面占位符已按当前平台替换）：

- **前端**：route → page/component → hook/store → api → formatter → 表单校验/状态反馈（读**已自动拉取的开发仓库** `{{CODE_REPO_DIR}}`，分支 `{{CODE_REPO_DIR}}`；页面代码在 `{{CODE_REPO_DIR}}/` 下）。
- **H5 端（MES 平台）**：读 `{{CODE_REPO_DIR}}`，分支 `{{CODE_REPO_DIR}}`。
- **后端**：controller → service → dao/mapper → 枚举/返回结构；字段组装、校验规则、空值、状态流转（读**已自动拉取的开发仓库** `{{CODE_REPO_DIR}}`，分支 `{{CODE_REPO_DIR}}`）。
- **代码来源红线**：白盒核对一律用 `list_directory` + `read_file` 读**已自动拉取到 {{CODE_REPO_DIR}} 的开发仓库**。**不要用 `grep_code(scope='frontend'|'api'|'backend')` 检索 `{{CODE_REPO_DIR}}` 知识库 源代码目录/源代码目录、线上前端接口索引或线上后端网关代码** —— 那些都是**脱敏的正式环境代码**（`scope='api'` 命中的线上前端接口索引同属正式环境），与开发分支可能不一致，用它做证据会判定错被测版本。知识库只用于 `glob_files / grep_code` 查页面映射，或非测试身份的代码对齐参考；**MES 平台没有知识库**，一律以本地开发仓库为准。

### Step 2 逐条核对

每条用例回答：

- 实现归属：前端 / 后端 / 前后端联动 / 外部依赖或运行时？
- 前端是否实现了自己负责的部分？
- 后端是否实现了自己负责的部分？
- 综合是否符合用例预期？代码证据是否闭环到最终消费点？
- 存在 bug / 风险 / 仍需联调 / 无法静态验证？

### Step 3 三档判定

按 `qa-conventions.md` 的三档口径判定：

- ✅ 源码可证：证据闭环，符合预期。
- ⚠️ 仍需联调：涉及真实运行数据 / RPC / 三方系统 / 权限树 / 定时任务等，源码看实现了但需运行确认。
- ❌ 无法静态验证：仓库/目录缺失、代码不在授权范围、纯依赖运行时。

**归类要保守**：能闭环就判「源码可证」，不滥用「无法验证」；确实缺输入才降档，并写明原因。

### Step 4 记录与落位

- 每条核对结果写入 `{{TEST_OUTPUT_DIR}}/work/<任务slug>/review-log.md`：`用例编号 | 实现归属 | 结论(三档) | 代码证据(文件:行/函数/字段) | 说明`。
- 完成后对照 `qa-case-ledger` 台账做覆盖对账，未核对项必须补测或明确归档。

## 完成前检查

- [ ] 所有原始用例都有核对记录，无「未核对」
- [ ] 每条结论都有代码证据，且关键字段/状态追到最终消费点
- [ ] 非通过态按三档正确归类，未把「无法验证」当「通过」

## 下一步

- 全部核对完 → `qa-report` 生成正式测试报告。
