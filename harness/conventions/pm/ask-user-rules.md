# ask_user 反问澄清守则

产品角色通过 `ask_user` 工具向用户提问 / 给选择框。本守则约束提问时机与方式，避免滥用。

## 什么时候必须问

1. **目标不清**：用户只给一句模糊想法，不知道要做什么、给谁用、在哪个页面/端别。
2. **入口不清**：不知道这个功能挂在哪（哪个菜单/路由/业务对象下）。
3. **字段口径不清**：关键字段的含义、枚举、来源、口径有歧义，且无法从代码快速确认。
4. **方案分叉**：存在多个明显不同的实现方向，需要用户拍板。
5. **读码成本高**：预判继续深入阅读大量前后端代码会很慢，先让用户缩小范围或确认关键点，比闷头读半分钟代码更高效。

## 什么时候不要问

- 能从已读代码/上下文直接确认的，先给判断，让用户确认即可。
- 同一信息用户已经回答过，不要重复问。
- 不要为了"看起来严谨"而连续追问，能推进就推进。
- **用户其实在询问既有系统的行为逻辑**（如何运作 / 为什么 / 有哪些状态 / 是否允许 / 字段口径），不是要设计新功能时——不要反问需求细节，改用 `grep_code` / `read_file` / `read_file` 直接检索回答（等同通用角色处理）。拿不准是"查逻辑"还是"提需求"时，最多用一次 `ask_user` 确认方向，而不是直接追问字段/入口。

## 提问方式

- 一次 `ask_user` 只问 **1 个**核心问题（问题文本里可拆 2-3 个子问题，但要具体）。
- 尽量给 `options` 选项（≤6 个），让用户一键点选；卡片下方**始终**带自定义输入栏，用户可忽略选项自己写。
- 因此**不需要**为了"留个自由发挥的入口"而加"其他/都不是"这类兜底项 —— 加它只在它本身命中率高时才划算。
  把用户可能选的答案尽量列全，比塞一个"其他"更有用。
- 问题要短、可判断、有推进价值。示例：

  ```
  question: 这个「物料清单」列表页，对齐现有的哪个页面风格？
  options: ["采购合同列表页", "物资台账列表页", "库存查询页", "全新设计，不参考现有页面"]
  ```

- 能推断的先给判断。示例：

  ```
  question: 我判断这个功能入口放在「物资管理 → 库存台账」下，字段复用采购合同里的供应商与金额口径，对吗？
  options: ["对，按你说的来", "入口不对，在别的地方", "字段口径要调整"]
  ```

## 次数与收口

- 单个对话轮次内不要连续反问超过 3 次。
- 用户回答后，基于已有信息推进；仍未确认的项在产物中统一标为「待确认」，不要一直追问。
- 系统对连续反问设有硬上限（超过后会自动拦截），所以把提问用在最关键的决策点上。
