# 测试报告固定结构（qa-report 输出模板）

报告用于归档、复盘，并可作为提测/验收依据。**结论前置，数据支撑在后**；数据来源必须明确标注，不编造。

## 固定章节顺序

1. **测试结论**（最前面）
   - 判定状态：`测试通过` / `测试不通过` / `有条件通过（需修复后回归）`
   - 覆盖统计：总用例数 / 通过 / 失败 / 未执行 / 仍需联调 / 无法静态验证
   - 关键问题数（阻塞性缺陷数）
   - 一句话风险提示
2. **测试范围与输入**
   - 被测代码路径（含分支/版本信息，若可确认）
   - 测试用例来源（文件路径或描述）
   - 测试类型：白盒（源码静态审查）/ 黑盒（引导式页面操作）
   - 被测模块清单（被检查工程/目录表）
3. **关键问题**（按严重度排序）
   - 每条：问题描述、复现/对应代码位置、影响、建议
4. **风险汇总**
   - 仍需联调项、无法静态验证项、未覆盖范围、数据/环境限制
5. **详细结果**
   - 逐条用例表格：`用例编号 | 模块 | 步骤/预期 | 结论(三档) | 代码证据 | 说明`
6. **用例覆盖台账**
   - 原始用例编号与标题清单，全部用例必须出现在台账中，标注是否已核对
7. **附录（可选）**：黑盒测试的步骤回放记录、截图路径等

## 统计口径

- 状态枚举：`通过` / `失败` / `未执行` / `仍需联调` / `无法静态验证`。
- 通过率 = 通过数 / 总用例数（总用例不含「未执行」；分母口径在报告中写明）。
- 「关键问题」= 已确认的缺陷/不符合预期的用例；「风险」= 未闭环但不足以定性的项。
- **最终报告不允许有「未核对」的原始用例**：未覆盖的要么补测，要么明确归入「未执行/无法静态验证」并说明原因。

## 质量要求

- 每条详细结果都必须有「代码证据」（文件路径:行/函数/字段）或页面证据。
- 结论与数据不矛盾：判定「测试通过」时关键问题数必须为 0。
- 缺失字段（人员、时间、环境、未覆盖范围等）标 `TODO: 人工确认`，不编造。
- 文件名：`{{TEST_OUTPUT_DIR}}/<任务slug>-测试报告.md`；过程产物落 `{{TEST_OUTPUT_DIR}}/work/<任务slug>/`。
